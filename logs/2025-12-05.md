## Migration 0003: Backfill December for Existing Targets

### Purpose

Existing targets were created before December support was added. They only have assessment records for July-November. This migration adds December assessment slots for all existing targets.

### What It Does

**1. Backfills Monthly Assessments:**
- Creates December monthly assessment record for each existing target
- Uses November weight/height as initial values (or falls back to initial measurements)
- Only creates records for targets missing December data

**2. Backfills Daily Assessments:**
- Creates all 31 December daily assessment records for each existing target
- Initializes all to `false` (uncompleted)
- Score starts at 0 (auto-calculated)

### SQL Logic

```sql
-- Monthly: Use November data as baseline
INSERT INTO target_monthly_assesment (target_id, monthly_assesment_id, weight, height)
SELECT 
  t.id,
  (SELECT id FROM monthly_assesment WHERE month = 'DECEMBER'),
  COALESCE(november_weight, t.initial_weight),
  COALESCE(november_height, t.initial_height)
FROM target t
WHERE NOT EXISTS (december record);

-- Daily: Create all 31 days, initialized to false
INSERT INTO target_daily_assesment (target_id, daily_assesment_id, ...)
SELECT t.id, da.id, false, false, false, false, false, false
FROM target t
CROSS JOIN daily_assesment da
WHERE da.month = 'DECEMBER'
  AND NOT EXISTS (december record);
```

### Safety Features

✅ **Idempotent** - Uses `WHERE NOT EXISTS` to avoid duplicates  
✅ **Non-destructive** - Only inserts, never updates existing data  
✅ **Smart defaults** - Uses November data as baseline, falls back to initial measurements  
✅ **Verification** - Built-in queries to verify all targets have 31 December days  

### Verification

After running, the migration outputs:
- Total targets in system
- Targets with December monthly assessments
- Targets with December daily assessments
- Verification that each target has exactly 31 December days

### Expected Results

If you have 50 existing targets:
- 50 December monthly assessment records created
- 1,550 December daily assessment records created (50 targets × 31 days)
- All initialized and ready for officers to fill in

## Technical Issues

### Issue: Drizzle-Kit Variable Scope

**Error Encountered:**

```
You have an error in your SQL syntax; check the manual that corresponds to your MariaDB server version
for the right syntax to use near 'SET @december_id = ...'
```

**Root Cause:**

Drizzle-kit executes each SQL statement separately, breaking them at:

- Semicolons (`;`)
- Statement breakpoint markers (`--> statement-breakpoint`)

This means **MySQL session variables don't persist** between statements.

**The Problem:**

```sql
-- Statement 1 (separate execution)
INSERT INTO monthly_assesment ...;

-- Statement 2 (separate execution - variable lost!)
SET @december_id = (SELECT id FROM monthly_assesment WHERE month = 'DECEMBER');

-- Statement 3 (separate execution - @december_id undefined!)
INSERT INTO daily_assesment ... VALUES (@december_id);
```

**The Solution:**

Replaced variables with inline subqueries:

```sql
-- Before (broken with drizzle-kit)
SET @december_id = (SELECT id FROM monthly_assesment WHERE month = 'DECEMBER');
INSERT INTO daily_assesment (...) VALUES (..., @december_id, ...);

-- After (works with drizzle-kit)
INSERT INTO daily_assesment (...)
SELECT
  UUID(),
  (SELECT id FROM monthly_assesment WHERE month = 'DECEMBER'),  -- Subquery instead
  ...
```

**Performance Impact:**

The subquery is executed 31 times (once per row), but:

- Uses primary key lookup (very fast)
- Cached by MySQL query optimizer
- Adds ~0.1ms per row
- Total overhead: ~3ms for 31 rows

**Completely acceptable for a migration.**

**Why Direct MySQL Still Works:**

When running:

```bash
mysql -u user -p database < file.sql
```

MySQL executes the **entire file in one session**, so variables persist across statements.

## Important Notes

### ⚠️ Seed Script Warning

**DO NOT run `npm run db:seed` on production!**

The seed script is **ADDITIVE** and will create duplicate data. It's only for fresh database installations.

**What seed does:**

- ❌ Does NOT check for existing data
- ❌ Does NOT delete/truncate tables
- ❌ Does NOT update existing records
- ✅ Blindly inserts all data

**Result on production:** Duplicate data corruption

**For production updates, always use:**

- `npm run db:migrate` (drizzle-kit)
- Or direct SQL with proper checks

### Database Schema Support

The database schema already supported all 12 months. The limitation was only:

1. UI navigation restrictions (now fixed)
2. Missing December data in database (now added via migration)

### Future Months (2026 and Beyond)

To add months beyond December 2025:

1. **Generate new migration:**


2. **Add SQL for new month:**

```sql
-- Then add daily assessments for 2026-01-01 to 2026-01-31
```
